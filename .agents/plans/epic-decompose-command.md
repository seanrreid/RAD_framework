## Context
The RAD flow today starts at `/rad-research`; there is no product-layer step that
shapes a multi-issue GitHub epic into stories before the team commits to a slice.
The rad-additions bundle includes an epic-decompose skill, but it is wired to
retired concepts (plan PRs, `RAD_POLICY.md`, `.claude/agents/` as inputs). This
plan re-homes it as an architect-only `/rad-epic-decompose` command that produces
a reviewable "Gate 0" shaping artifact upstream of `/rad-research` — using this
repo's actual conventions (architect role gate, platform abstraction, `.agents/`
artifact dirs). It does not generate plan files and never calls `/rad-research`
or `/rad-plan`; its stories are inputs the team feeds downstream.

## Scope
| In scope | Out of scope |
|---|---|
| `scripts/fetch-epic.sh` — fetch an epic + its child issues (number or URL), platform-gated | Non-GitHub platforms (GitLab/Bitbucket epic models differ) — v1 GitHub-only, documented |
| `.claude/commands/architect/rad-epic-decompose.md` — the architect-only Gate-0 command | Generating wave-structured plan files (that's `/rad-plan`, downstream) |
| Output a shaping artifact to `.agents/epics/epic-[N]-[slug].md` | Calling `/rad-research` or `/rad-plan` internally |
| Document the Gate-0 step in CLAUDE.md + a docs page | Auto-committing the artifact, opening a PR, or auto sign-off |

## Acceptance Criteria
1. `/rad-epic-decompose` exists at `.claude/commands/architect/rad-epic-decompose.md`
   and gates on `scripts/check-role.sh architect` before fetching any issue,
   mirroring `rad-approve`'s authority pattern.
2. Given an epic issue number or URL, the command produces
   `.agents/epics/epic-[N]-[slug].md` containing per-child-issue stories
   (What / Why / Acceptance criteria / Affected domains / Recommended plan
   structure / Open questions) plus an epic-level section (execution order,
   cross-cutting concerns, open questions, architect sign-off checklist) — and
   produces no plan files and makes no call to `/rad-research` or `/rad-plan`.
3. `scripts/fetch-epic.sh` accepts an issue number or URL, is platform-gated via
   `scripts/detect-platform.sh`, fetches the epic and its deduplicated child
   issues on GitHub, and exits with a clear documented message on non-GitHub /
   manual platforms (v1 GitHub-only limitation).
4. The command and artifact reference only current conventions — no plan PRs, no
   `RAD_POLICY.md`, no `.claude/agents/` as inputs; the command reads `CLAUDE.md`,
   `.agents/architecture/`, and recent `.agents/plans/` for context, and positions
   its output upstream of `/rad-research`.
5. CLAUDE.md's Workflow section documents `/rad-epic-decompose` as the Gate-0 step
   upstream of `/rad-research`, and `.agents/epics/` is named as its artifact home.
6. `fetch-epic.sh`'s URL→number extraction and its unsupported-platform failure
   path are covered by a test in the repo's bash-harness style — stubbed
   environment, no live network.

## Execution Notes

### Do Not Touch
- `.claude/agents/` — generated by `/rad-design`; epic-decompose reads context
  from `.agents/architecture/`, never hand-edits agents.
- `.agents/plans/*.md` `Status:` fields — owned by the harness/gates; the command
  must not write or mutate plan status.
- The `/rad-research` and `/rad-plan` command files — this feature sits upstream
  and is invoked separately; it does not modify or call them.

### Key Files
- `.claude/commands/architect/rad-approve.md` — the architect-only gate pattern
  (`scripts/check-role.sh architect`) and front-matter/`$ARGUMENTS` style to mirror.
- `.claude/commands/architect/rad-design.md` — the artifact-producing command
  shape (Status/Created headers, write-to-`.agents/[dir]/[slug].md`).
- `.claude/commands/team/rad-adopt.md` — existing platform-aware `gh`/`glab`
  issue-fetch logic to reuse rather than reinvent.
- `scripts/detect-platform.sh`, `scripts/rad-label.sh` — platform gate and
  best-effort label mirroring conventions.
- `~/Downloads/rad-additions/rad-extensions` — the source SKILL.md and
  `fetch-epic.sh` to harvest the story/artifact structure from (strip retired
  references during re-home).

### Reminders
- Slugs are kebab-case; artifact carries `Status:` and `Created: YYYY-MM-DD`.
- The artifact is a discovery/shaping doc — the command writes the file but does
  NOT auto-commit, open a PR, or flip any approval status. The architect commits
  and signs off manually.
- Do not mutate GitHub issues unless `RAD_UPDATE_ISSUES=true`; default off.
- GitHub-only is intentional for v1 — fail clearly on other platforms, don't
  half-implement a GitLab path.

## Non-Goals
- No wave-structured plan generation — that is `/rad-plan`, downstream.
- No internal calls to `/rad-research` or `/rad-plan`; stories are inputs, not
  triggers.
- No auto-commit of the artifact, no PR, and no automatic architect sign-off —
  the architect commits and signs off manually.
- No `RAD_POLICY.md` dependency and no GitHub issue mutation unless
  `RAD_UPDATE_ISSUES=true`.
- No GitLab/Bitbucket/Forgejo support in v1 — GitHub-only, documented; their epic
  models differ enough to warrant a separate effort.

## Out-of-Scope Dependencies
None.

## Risks
- **Child-issue discovery is heuristic.** Native sub-issues, body references, and
  milestone matching can over- or under-collect. Mitigation: dedupe and surface
  the child set in the artifact for the architect to correct before sign-off.
- **Platform coupling.** GitHub-only could surprise non-GitHub users. Mitigation:
  explicit `detect-platform.sh` gate with a clear message and a documented
  limitation.
- **Artifact drift from conventions.** Re-home could leave stale plan-PR wording.
  Mitigation: AC#4 + review against current CLAUDE.md conventions.
